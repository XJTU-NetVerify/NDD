# MTPNDD N-Queens 操作间并行化实验报告

> 本文档专门记录**操作间并行化**（inter-operation parallelism）的设计、实现、
> 实验结果及 Phase 3 并行化的尝试与失败分析，供论文写作使用。

---

## 1. 背景与问题定义

### 1.1 已有的操作内并行

MTPNDD 的核心操作（`mtpndd_and`、`mtpndd_or`、`mtpndd_not`）已通过 Lace
工作窃取框架实现了**操作内并行**（intra-operation parallelism）：每次 AND/OR
调用会对递归子问题 SPAWN Lace 任务，多个 worker 在单次操作的递归树内部并发工作。

操作内并行的扩展性受制于单次操作的递归深度和子问题数量，对于规模较小的操作
（Phase 1 的 OR 项、Phase 2 的 cell 约束），单次操作无法占满所有 worker。

`MTPNDD_SPAWN_THRESHOLD`（默认值 2）控制操作内并行的启动粒度：
当一个节点的两棵子树的出边乘积 ≥ 该阈值时才 SPAWN。从阈值 64 降至 2 后，
N=12、5 workers 下时间从 4.97s 降至 3.82s（**+24%**，commit `4d444e7`）。

### 1.2 操作间并行的动机

N-Queens 问题的构建过程分三个阶段：

```
Phase 1  构建 n 个 row-OR 项：or_batch[0..n-1]
Phase 2  构建 n² 个 cell 蕴含项：imp_batch[0..n²-1]
Phase 3  顺序折叠 AND：queen = AND(AND(...AND(TRUE, c₀)...), cₙ₊ₙ²₋₁)
```

Phase 1 和 Phase 2 的所有子任务**相互独立**，天然适合并发执行。
串行版（`nqueens_benchmark.c`）用顺序 for 循环逐个构建，n² 个子任务只能
依次占用 worker，多余的 worker 在操作间处于空闲或工作窃取状态，利用率低。

**操作间并行**的目标：将 Phase 1 和 Phase 2 的全部子任务同时作为 Lace 任务
提交，让所有 worker 在任务粒度上并发竞争，充分利用多核。

## 2. 实现方案

### 2.1 新增并行 Benchmark

新增 `nqueens_parallel_benchmark.c`，保持与串行版完全相同的公式编码和
Phase 3 顺序折叠逻辑，仅将 Phase 1 和 Phase 2 改为外层并发 SPAWN/SYNC。

| 文件 | 角色 |
|------|------|
| `nqueens_benchmark.c` | 串行版（Phase 1+2+3 全顺序，依赖操作内并行）|
| `nqueens_parallel_benchmark.c` | 并行版（Phase 1+2 并发，Phase 3 顺序）|

两个 binary 使用完全相同的 `mtpndd_pal_config_t` 配置，便于控制变量对比。

### 2.2 Phase 1 与 Phase 2 的 SPAWN/SYNC 实现

```c
LACE_ME;   // 获取主线程 Lace worker 上下文

/* ---- Phase 1：n 个 row-OR 任务并发 ---- */
for (size_t i = 0; i < n - 1; i++) {
    SPAWN(par_build_row_or, i, n);
}
or_batch[n-1] = CALL(par_build_row_or, n-1, n);   // 最后一个本地执行
for (int i = (int)n-2; i >= 0; i--) {             // LIFO 顺序 SYNC
    or_batch[i] = SYNC(par_build_row_or);
}

/* ---- Phase 2：n² 个 cell 任务并发 ---- */
for (size_t k = 0; k < total_cells - 1; k++) {
    SPAWN(par_build_cell, k/n, k%n, n);
}
imp_batch[total_cells-1] = CALL(par_build_cell, n-1, n-1, n);
for (int k = (int)total_cells-2; k >= 0; k--) {
    imp_batch[k] = SYNC(par_build_cell);
}
```

SYNC 必须以 LIFO 顺序（与 SPAWN 相反）执行，这是 Lace 工作窃取语义的要求。

### 2.3 Lace 嵌套调用的安全性

`par_build_cell` 内部调用 `build_cell`，进而调用 `mtpndd_and`/`mtpndd_or`。
这些操作使用 `RUN()` 宏（= `LACE_ME + CALL`）。

当 `par_build_cell` 被 worker N 窃取执行时，`LACE_ME` 通过 `lace_get_worker()`
获取 worker N 自己的上下文，内部 SPAWN/SYNC 在 worker N 的 deque 上操作，
与其他 worker 的队列完全隔离，语义正确。操作内并行（intra-op）与操作间并行（inter-op）
因此可以**安全嵌套**：一个被窃取的外层任务内部仍然可以触发操作内 SPAWN。

### 2.4 引用计数与 GC 保护

每个 Lace 任务返回 **+1 ref** 的节点指针，使节点在 SYNC 之前不会被 GC 回收：

```c
TASK_IMPL_2(mtpndd_t *, par_build_row_or, size_t, row, size_t, n) {
    mtpndd_t *cond = &MTPNDD_FALSE;
    mtpndd_ref(cond);
    for (size_t j = 0; j < n; ++j) {
        mtpndd_t *next = mtpndd_or(cond, v);
        mtpndd_ref(next);      // 立即保护，防止 GC 触发前被回收
        mtpndd_deref(cond);
        cond = next;
    }
    return cond;               // 返回 +1 ref，所有权交给调用方
}
```

SYNC 后调用方持有 ref，Phase 3 结束后统一 deref。

### 2.5 BDD 表大小调整

并行版中 n² 个 cell 同时存活于内存，所需 BDD nodetable 大于串行版。
并行版对小 N 设置 128K 下限（串行版为 1K）：

```c
// 串行版：fmax(1000.0, pow(4.4, n-6) * 1000.0)
// 并行版：floor 提升至 131072（128K）
size_t bdd_size = 1 + (size_t)fmax(131072.0, pow(4.4, (double)n-6.0) * 1000.0);
```

N≥10 时两者公式结果相同（≥512K），无差异。

### 3.4 Amdahl 定律验证

设 Phase 1+2 占总时间的比例为 $f$，p 个 worker 的理论加速上限为：

$$S = \frac{1}{(1-f) + f/p}$$

**N=8, w=6 验证**：

Phase 1+2 约占 15ms / 33ms ≈ 45%，代入 p=6：

$$S = \frac{1}{0.55 + 0.45/6} \approx 1.55\text{x}$$

实测 1.57x，与理论吻合。

**N=12, w=6 验证**：

Phase 1+2 约占 0.15s / 3.55s ≈ 4%，代入 p=6：

$$S = \frac{1}{0.96 + 0.04/6} \approx 1.04\text{x}$$

实测 0.99x，Phase 3 占 96% 的时间将并行收益完全压制至噪声范围。

## 4. Phase 3 并行化：原因分析与三次尝试

Phase 3 是 N-Queens 中耗时最长的阶段，对 N=12 占总时间约 97%。
以下记录了三次尝试并行化 Phase 3 的方案，以及全部失败的原因分析。

### 4.1 为什么 Phase 3 难以并行化

Phase 3 的结构是**严格的顺序依赖链**：

```
queen₀ = TRUE
queen₁ = AND(queen₀, c₀)
queen₂ = AND(queen₁, c₁)
...
queenₙ₊ₙ² = AND(queenₙ₊ₙ²₋₁, cₙ₊ₙ²₋₁)
```

每一步的输入 $\text{queen}_{k}$ 依赖上一步的输出 $\text{queen}_{k-1}$，
是严格的**数据依赖链**，不能直接拆分为独立并发任务。

顺序折叠之所以高效，在于其**渐进约束修剪**（progressive constraint tightening）特性：
每施加一个约束 $c_k$，queen 的 NDD 节点数单调不增：

$$|\text{queen}_k| \leq |\text{queen}_{k-1}|, \quad \forall k$$

Phase 3 后期，queen 已被前序约束大幅压缩，每步 AND 的代价极小。
这一特性是顺序折叠高效的根本原因，也是所有并行化尝试失败的根源——
任何破坏渐进修剪的方案都会导致中间结果膨胀，反而更慢。

### 4.2 尝试一：树形并行规约（mtpndd_and_reduce）

**方案**：用 Lace 树形 reduce 替代顺序 fold：

```
Level 0:  [c₀,  c₁,  c₂,  c₃,  ..., c₁₅₅]        (156 项，N=12)
Level 1:  [AND(c₀,c₁), AND(c₂,c₃), ...]            (78 项并发)
Level 2:  [AND(L1[0],L1[1]), ...]                   (39 项并发)
...
Level 8:  [queen]
```

理论深度从 $n + n^2$ 步降至 $\lceil \log_2(n+n^2) \rceil$ 步，理论上可充分并行。

**实测结果（N=12）**：程序触发 **OOM，被系统 SIGKILL**，无法完成。

**失败原因**：
树形规约在约束修剪发挥作用之前就将独立约束两两合并。
$\text{AND}(c_0, c_1)$ 的两个操作数各自是局部约束，节点数小；
但合并结果是两个约束的"联合"，节点数近似为二者之和，不经过修剪。
随着层数增加，中间 NDD 指数膨胀，N=12 的 156 项约束合并后的中间结果
超出内存上限。

### 4.3 尝试二：按行分组规约（row-level grouping）

**方案**：先在 Phase 2 内将每行 n 个格子约束并行 AND-reduce 为 `row_imp[i]`，
再在 Phase 3 只做 n 步顺序折叠（而非 n²）：

```
// 修改后的 Phase 2（每行内部并行规约）
row_imp[i] = AND(imp[i][0], imp[i][1], ..., imp[i][n-1])   并发 n² → n

// 修改后的 Phase 3（步数减少 n 倍）
queen = AND(AND(...AND(TRUE, or[0])..., or[n-1]), row_imp[0], ..., row_imp[n-1])
```

期望将 Phase 3 步数从 n² 降为 n，减少总 AND 次数。

**实测结果（w=4）**：

| N  | 原方案 cell-level fold (s) | row-level grouping (s) | 差异 |
|----|--------------------------|----------------------|------|
| 8  | 0.025 | 0.028 | 1.12x 更慢 |
| 10 | 0.192 | 0.399 | **2.1x 更慢** |
| 12 | 4.887 | 6.725 | **1.4x 更慢** |

**失败原因**：
单个 `imp[i][j]` 是描述格子 (i,j) 局部冲突关系的小约束，节点数少。
而 `row_imp[i] = AND(imp[i][0], ..., imp[i][n-1])` 是该行 n 个局部约束的合集，
未经 queen 的渐进修剪，节点数接近 n 倍。
Phase 3 中 `AND(queen, row_imp[i])` 每步的 RHS 更大，代价更高，
总时间反而增加。N 越大，n 越大，效果越差（N=10 时 2.1x 更慢）。

**关键认识**：Phase 3 的高效来自于用"已充分压缩的 queen"作为 LHS，
而不是来自于操作步数少。步数减少 n 倍，但每步代价增加超过 n 倍，净效果为负。

### 4.4 尝试三：交错折叠顺序（interleaved fold）

**方案**：将 Phase 3 的折叠顺序从
"先折 n 个 OR 项，再折 n² 个 imp 项（行优先）"
改为"按行交错：对每行 i，先折 `or[i]`，再折 `imp[i][0..n-1]`"：

```
// 原顺序（先全部 OR 后全部 imp）
queen = AND(AND(...AND(TRUE, or[0])..., or[n-1]),
            imp[0][0], ..., imp[0][n-1],
            imp[1][0], ..., imp[n-1][n-1])

// 交错顺序（行内 OR + imp 一起处理）
for row i in 0..n-1:
    queen = AND(queen, or[i])
    for col j in 0..n-1:
        queen = AND(queen, imp[i][j])
```

期望 queen 在进入第 i+1 行前已包含第 i 行的全部约束，使后续 AND 的 LHS 更小。

**实测结果（DEBUG=2 build，w=4）**：

| N  | 原序（先全 OR 后全 imp）(s) | 交错序（行内 OR+imp）(s) | 差异 |
|----|--------------------------|----------------------|------|
| 10 | 0.316 | 0.449 | **1.4x 更慢** |
| 11 | 1.42  | 2.24  | **1.6x 更慢** |
| 12 | 7.32  | 11.43 | **1.6x 更慢** |

**失败原因**：
交错折叠让 queen 过早积累**跨 field 约束**，破坏了 `op_cache` 的时间局部性。
AND 操作缓存基于 (a, b) 指针对查找：当 queen 的内部结构因交错而变化规律不同时，
缓存命中率从 14.7% 下降至约 9%，每步 AND 需要完整重算。
"更受约束"的 queen 并不等于"更小的 NDD"——NDD 节点数由约束的**结构兼容性**
决定，而非仅仅由约束的严格程度决定。缓存局部性损失的代价超过了理论上 queen
缩小的收益。

## 5. 分析汇总

### 5.1 Phase 3 不可并行化的根本原因

| 方案 | 核心思路 | 失败原因 |
|------|---------|---------|
| 树形规约 | 降低折叠深度至 O(log n) | 破坏渐进修剪，中间 NDD 指数膨胀，OOM |
| 行分组规约 | 减少 Phase 3 步数至 n | 每步 RHS 更大，步数 ÷n 但代价 ×n，净效果为负 |
| 交错折叠顺序 | 提前施加跨行约束 | 破坏 op_cache 时间局部性，命中率下降，代价增加 |

三种方案的共同错误假设是：**减少操作步数或使 queen 更受约束 = 更快**。
实际上 Phase 3 的效率来源于顺序折叠对 op_cache 局部性的维护和对渐进修剪的利用，
任何打破这两个条件的方案都会反效果。

### 5.2 操作间并行化的适用范围总结

| 阶段 | 并行化状态 | 最大加速比（6 workers）| 说明 |
|------|-----------|-------------------|------|
| Phase 1（row-OR）| ✅ 已实现 | 包含在整体加速中 | n 个独立任务，并发 SPAWN |
| Phase 2（cell imp）| ✅ 已实现 | 包含在整体加速中 | n² 个独立任务，并发 SPAWN |
| Phase 3（AND fold）| ❌ 不可并行 | — | 严格数据依赖链，三种方案均失败 |
| **整体（N=7–10）** | ✅ 有效 | **1.19–1.57x** | Phase 1+2 占比 15–45% |
| **整体（N=11–13）** | ❌ 无效 | ≈1.00x | Phase 3 占比 >95%，并行收益被淹没 |

### 5.3 未来可行方向

Phase 3 的根本瓶颈是**全局顺序依赖链**，若要在大 N 下获得并行收益，
需要从算法层面重构问题，而非优化当前折叠顺序：

- **对称性分解**：利用棋盘的旋转/反射对称群（最多 8 倍对称），将问题分解为
  k 个独立子问题，各自独立完成 Phase 1+2+3，最后 OR 合并。
  此方案使 Phase 3 本身也可并行，但需要正确实现对称坐标变换，工程复杂度高。
- **分块折叠 + 合并**：将约束序列均分为 k 段，各段独立折叠后再用树形 AND 合并。
  每段初始 queen=TRUE（非全局 queen），段内可保持渐进修剪，段间的合并代价需评估。
