# MTPNDD 并行优化实验结果汇总

## 测试平台

HP Zhan 86 Pro G2 MT, 6-core (12-thread), Linux 6.19.9

## 优化内容

### 已合入源码的改动

1. **BDD spawn depth cutoff** (`sylvan_bdd.c`)
   - API: `sylvan_set_spawn_depth_cutoff(0)` 可禁用 BDD 内部并行
   - 默认 -1（不限制），sre-ndd 当前未启用
   - 独立效果：对 sre-ndd <5%，因为 BDD label 小、SPAWN 本就很少

2. **两阶段 AND (Filter-then-Recurse)** (`mtpndd_node.c`)
   - 当 `E_a * E_b >= 16` 且 workers > 1 时启用
   - Phase 1: 串行遍历所有 edge pair，BDD label filter
   - Phase 2: 对 surviving pairs 并行 SPAWN 递归
   - 阈值 `MTPNDD_AND_TWO_PHASE_THRESHOLD = 16`

### 编译配置

- `MTPNDD_SPAWN_THRESHOLD = 2`（默认，未改）
- `MTPNDD_LOG_LEVEL = 1`（INFO，无 per-call timing）
- BDD spawn depth cutoff = -1（默认，未启用）

## 分析

### 1. 全面性改善：所有配置都变快了

每个 (dataset, MF, workers) 组合都有 2-15% 的提升，w=1 也有 3-5%。
这表明有一部分改善来自代码本身的变化（两阶段 AND 的代码路径差异、
编译器优化差异），不全是并行效果。

### 2. 多 worker 改善幅度更大

fattree08 k=1: w=1 -2.5%, w=6 -5.2%
fattree12 k=1: w=1 -2.9%, w=6 -6.0%
fattree12 k=2: w=1 -3.3%, w=6 -6.0%

多 worker 时额外的 2-3% 改善来自两阶段 AND 减少了 Lace 调度热点。

### 3. MF=3 fattree12 改善最大

旧：479.2s (w=1) → 新：412.0s (w=1)，**-14.0%**。
旧：403.7s (w=4) → 新：363.3s (w=4)，**-10.0%**。

MF=3 的 NDD 操作量最大（更多 merge 轮次），两阶段 AND 的 filter
效果更明显——更多的 false pair 被提前剪枝，减少了无效递归。

### 4. Worker scaling 仍然受限

fattree12 k=1: w=1 19.9s → w=6 21.6s（仍然 +8.4% 退化）。
根因不变：Java 串行调 JNI，MTPNDD 内部并行粒度不足。

## Lace Profiling 辅助分析

在 SPAWN_THRESHOLD=2 + LOG_LEVEL=2 + Lace stats 下的 profiling 显示：

| 指标 | w=1 | w=4 |
|------|----:|----:|
| Steal tries | 0 | 240M |
| Steal success rate | - | 0.80% |
| Steal search (CPU) | 0ms | 54,591ms |
| CPU efficiency | 100% | 23.7% (work/total CPU) |

提高 SPAWN_THRESHOLD 到 16 可将 steal tries 从 240M 降到 2.5M（-99%），
消除多 worker 退化。但也消除了并行度——w=4 和 w=1 完全持平。

**结论**：MTPNDD 内部的 task-level 并行在当前 sre-ndd workload 上
无法有效利用多核。需要在 Java 应用层引入并行（如并行处理不同路由器
的 BGP 计算）才能实现真正的加速。
