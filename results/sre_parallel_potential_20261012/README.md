# N-Queens 能扩展，SRE 还能否取得显著并行收益？

**还有空间，但必须区分相对 Java 的加速与 native 自身的多核扩展性。** 本轮实测确认：当前核心在 N-Queens 上仍有约 3.1–3.2 倍的六线程加速；SRE 调整 GC 水位后已达到约 2.77 倍原 Java 的参考性能，但六线程相对自己的单线程仍只有约 1.01 倍。进一步把标签任务打开，任务数增长一个数量级，耗时没有显著改善。下一步需要扩大应用任务粒度，尤其是占主要时间的 SRC。

本轮新增 22 次独立进程：N-Queens 8 次，SRE 14 次；每种配置重复两次。使用上一轮冻结的同一 native 核心构建与 NDD JAR，没有修改核心算法、SRE 编译类或默认 GC 策略。CPU 固定 0,2,4,6,8,10，native budget 3 GiB；SRE 保持 JVM 8 GiB、RSS 上限 12 GiB、F 全 BCDD、原编码/trim/顺序。全部解数、完整 RIB 文本与数值计数、条件指纹、reachability CSV 校验通过，并与上一轮九组结果对照。[审计](checks.json)、[均值和范围](summary.json)。

## GC 水位实验：找到一块可直接改善的开销

同一 3 GiB native 预算中，默认 adapter 水位为 1075 MiB，约 35%。本轮仅通过已有属性改为 1228 MiB，约 40%；未扩大 native/JVM/RSS 上限。

|---|---:|---:|---:|
| 前一轮默认 35%，参考 | 193.145 | 179.131 | 72 / 77 |
| 本轮 40% | 116.906 | 115.644 | 4 / 4 |

35% 行和原 Java 320.645 秒来自[前一轮冻结控制矩阵](../sre_deep_optimization_20261012/README.md)，不是本轮重新交错的控制组；两轮实际运行核心/JAR 哈希一致。相对这两个参考，六线程改善约 1.55×，达到约 **2.773× 原 Java**。一线程也几乎同幅改善，六线程自身加速仅 **1.011×**。

native1/6 峰值 RSS 均值为 3532.0/3199.3 MiB，native1 两次为 3936.7/3127.3 MiB，内存波动较大。GC 水位调整主要改善转发和可达性阶段，SRC 几乎仍占满关键路径；标签 GC 各 8 次。当前回收按 nativeBytes 判断，该计数包括缓存、表、保留 slab；回收后仍接近水位就容易很快再次回收并清缓存。实验支持优化此策略，但未直接记录每次回收的释放量与耗时，不能把全部时间差精确归为 GC 停顿。

-Dsre.ndd.gcHighWaterMiB=1228

配套 workers=6、cache=16777216、memoryMiB=3072、labels=false。它是 12/MF3 的已测配置，不是所有网络/预算的通用默认。benchmark 增加了 `--gc-high-water-mib 1228`，可原样复现；默认策略没有被偷偷替换。[数据](gc40/runs.csv)、[配置](gc40/metadata.json)。

## 为什么 SRE 没有 N-Queens 的自身加速

1. **独立工作暴露在不同层级。** N-Queens 的大型组合能在 NDD 子图层递归拆开。SRE 许多条件的复杂性位于边标签，NDD 边本身很少；较早 profiling 的大多数子问题只有 0–3 个存活子任务，新版本还会过滤缓存命中。旧分布不是新版本的实时分布，但解释了只按边数拆分的局限。
2. **长任务图与大量短提交的区别。** N-Queens 一次 RUN，SRE 本轮大输入仍约 162 万次 external RUN。当前批处理限于一张优先级列表、一个路由器的规则或一次 DFS 节点的端口集合；更外层独立工作没有一起交给 Lace。调用数不是 JNI 独占时间的测量，但明显揭示了任务组织差异。
3. **SRC 的执行顺序仍强耦合。** BGP 逐 process 执行 updateRIB/routeOut，队列与优先级列表不断更新；priority_top 的 prefix 也按列表串行构造。对照可见六线程 SRC 比单线程略慢。源码存在串行依赖和提交，但这些事实不能直接换算为不可改变的串行比例。
4. **共享访存成本。** worker front cache 之后仍要访问分片锁保护的共享 cache/规范表。更多 worker 可能增加共享访存、重复 miss、任务交接和等待；需要测锁等待与 worker idle 才能确认各项比例，不能仅凭六线程较慢就判定某把锁是主要瓶颈。

## 下一步实现应改变什么

**第一步：把 GC 改成有反馈和滞回的资源策略。** 分开记录存活空间、保留 slab、固定 cache/table，以及每次 GC 的回收率。回收后设置必要的增长余量；低收益回收延长检查间隔，逼近真实预算再收紧。保留分配失败时保护输入、回收重试的路径。先做固定水位/动态策略的 1/6 workers、同预算对照，不能只提高水位掩盖内存问题。

**第二步：增加跨列表/跨路由器的 native 批次。** 多份不可变优先级请求一次进入 RUN，每份列表的 prefix 与选择成为完整子任务，结果在主线程沿原顺序提交。转发阶段也应一次提交多台路由器的完整条件计算。SRE 的 Java adapter、共享 memo、逻辑引用计数并不适合直接 parallelStream；继续共用一个 Lace pool，归并时再写 Java 表。BGP 只能批量计算已满足依赖的请求，不应直接并发改路由表或改变消息接收顺序。

**第三步：按源并行完整可达性查询。** 在转发/ACL 已固定之后，各源的路径状态可独立；将拓扑与 NDD 输入快照交给 native，由 source 任务持有局部路径/结果集合，再确定性合并 forest、in/out、PFEC 和统计。不能只返回 all-pair OR 而丢失原 API 的路径/计数。查询按内存预算分块；当前 NDD GC 仅在 admitted 操作之间运行，不能直接把所有源放进一个无限增长的 RUN。分块与任务根引用是实现的一部分。

先做跨优先级列表批次，以直接针对约 88–93 秒的 SRC 大头；随后做跨源查询。采样记录批次时长、独立请求数、实际缓存未命中、GC/归并和锁等待，任务不够粗就合并，而非继续增加 SPAWN。

## 能做到什么程度

**相对原 Java 约 3 倍已接近实测；native 自身六线程约 3 倍仍未实现。** 以本轮单线程 116.906 秒、SRC 88.218 秒作条件估算：如果 SRC 不变，其他所有工作即使理想六核化，仍需约 93.0 秒，自身加速约 1.26×。这不是 SRE 的固有上限，因为 SRC 的执行结构可以改变；它说明只优化可达性不足以得到 N-Queens 式扩展。

六核自身 3×/4× 在忽略同步与带宽成本的理想模型中，要求约 80%/90% 的工作可并行。新的宏观任务必须覆盖 SRC 大部分计算，并控制 GC、共享表和归并，才具备这个条件。下一轮合理的验证目标是先确认大输入自身 2×；3× 作为后续目标，不能根据源任务独立性就承诺最终倍数。
